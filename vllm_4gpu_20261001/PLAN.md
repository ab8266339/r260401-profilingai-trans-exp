## 2. 服务栈与模型

- vLLM **0.30.0**，torch 2.13.0+cu130，Python 3.12.14，独立 venv `~/venvs/vllm`（4卡机）。驱动 580.178.04。
- 服务参数（全部记录在每个配置的 `server_info.json` 里）：`--gpu-memory-utilization 0.90 --max-model-len 12288 --seed 0 --enable-prefix-caching --enable-prompt-tokens-details`，块大小用默认值（16）。
- 环境：`VLLM_USE_FLASHINFER_SAMPLER=0`（4卡机没有系统 CUDA 工具链，FlashInfer 采样器的 JIT 编不了；本实验用贪心解码，采样器实现不影响输出）。
- FP8 KV 配置加 `--attention-backend TRITON_ATTN`（vLLM 对 FP8 KV 的默认后端 FlashInfer 同样需要 JIT）。bf16 配置用自动选择的 FLASH_ATTN。**因此 bf16 与 FP8 之间的计时差混有注意力后端差异，只比较各自配置内的钉住/重放，不跨精度比时间**；字节数不受影响。

| 键 | 模型（ModelScope，修订号） | 权重精度 | 放置 |
|---|---|---|---|
| qwen3_4b | Qwen/Qwen3-4B（2c54d5a0） | bf16 | 卡 0 |
| qwen3_8b | Qwen/Qwen3-8B（26028140） | bf16 | 卡 1 |
| qwen3_14b_awq | Qwen/Qwen3-14B-AWQ（5a6fa840） | AWQ int4 | 卡 2 |
| qwen3_32b_awq | Qwen/Qwen3-32B-AWQ（c1456858） | AWQ int4 | 卡 3 |
| qwen25_72b_awq | Qwen/Qwen2.5-72B-Instruct-AWQ（409c86ad） | AWQ int4 | 4 卡张量并行 |

- 14B bf16 约 29.5 GB、32B bf16 约 65 GB，单张 32 GB 卡放不下，所以 14B 及以上用官方 AWQ 量化。Qwen3 没有 70B 级稠密模型，70B 级用 Qwen2.5-72B-Instruct-AWQ。
- 权重量化不改变 KV 的形状；KV 精度由 `--kv-cache-dtype` 单独控制。跨模型只比较字节与相对节省，不把不同量化的绝对时间当成规模效应。
- 理论 KV 字节/token = 2 × 层数 × KV 头数 × 头维 × 元素字节，由各模型 config.json 算出（bf16：4B 与 8B 为 147,456 B，14B 163,840 B，32B 262,144 B，72B 327,680 B；FP8 减半）。这是架构算术，不是测量；测量值来自分配器。

## 3. 工作负载（固定 token 轨迹）

- 提示词直接以 token ID 列表发送（completions 接口），不经过重新分词。token 取自各模型词表中形如「空格+3–10 个小写字母」的词元（Qwen 系 22,349 个），用工作量随机流抽取。
- 工作量随机流：`numpy.random.default_rng([20261001, τ0, rep+1000, session])`。它与臂、臂的先后、缓存盐都无关；热身用 rep = −1，不进结果。
- 一个会话 = 一条流水线。首级上下文 τ0 个 token；每级追加一条 50 token 的新指令；每级生成**恰好 128 token**（`min_tokens = max_tokens = 128`，`ignore_eos`，温度 0）；生成的 token ID 原样追加进上下文，下一级再追加新指令。这与式 (3) 的计量一致：钉住时后续级只需预填充新指令（加末尾不满一块的余数）。
- 两臂 token 数逐级完全相同；生成内容可能因数值差异不同（只作诊断，记录每级输出的哈希），但长度相同，所以稠密模型的 token 工作量相同。

## 4. 臂

| 臂 | 做法 | 代表 |
|---|---|---|
| pinned（钉住） | 每个会话一个固定 `cache_salt`，服务端复用本会话自己的 KV 块，只预填充新 token | 状态驻留在加速器上（AFS-C + 钉住 KV） |
| replay（重放，基线） | token 序列完全相同，但每一级换一个新的 `cache_salt`，强制整段重算；不加任何 nonce token | 无状态重放（论文比较的基线） |
| restore（存取，仅卸载配置） | 同钉住，但每级之前清空 GPU 前缀缓存（`reset_external=false`，保留 CPU 卸载层），会话前缀从主机内存恢复 | 状态驻留主机内存、按需恢复（F06：GPU 还是主机） |

- 每个格子内两臂（或三臂）按重复号交替先后（偶数 rep 正序，奇数 rep 逆序）。每个格子开始前清空全部前缀缓存（含 CPU 层）。
- 每个设置（τ0 × 并发 × 级数）先跑一次不计时热身，每臂一遍。
- 冒烟已核实：同盐第二次请求命中 240/256 token，异盐命中 0；钉住第 2–4 级命中整块前缀，重放各级命中 0；GPU 缓存清空后存取臂从 CPU 层命中 336/416 token；输出恰为指定长度（冒烟用 0.6B 模型、16 token 输出，**冒烟数字不作结果**）。

## 5. 因子与重复

| 配置 | 适用模型 | 格子（τ0, 并发, 级数） | 臂 | 重复 |
|---|---|---|---|---|
| main，bf16 KV | 4B / 8B / 14B / 32B（各占一卡，四卡同时跑） | (900,1,32) (900,4,32) (3400,1,32) (3400,4,32) (6700,1,8) (6700,4,8) (900,16,8) | pinned, replay | 10 |
| fp8，FP8 KV | 同上 | (900,1,32) (900,4,32) | pinned, replay | 10 |
| offload，bf16 KV + 32 GiB 原生 CPU 卸载 | 同上 | (900,1,16) (3400,1,16) | pinned, restore, replay | 10 |
| tp4，bf16 KV | 72B，TP=4 | main 去掉 (900,16,8) | pinned, replay | 10 |
| tp4_fp8，FP8 KV | 72B，TP=4 | (900,1,32) | pinned, replay | 10 |

- 深度 d ∈ {1, 2, 4, 8, 16, 32}：取同一条流水线的前 d 级。各级严格串行，前 d 级就是一条深度 d 的流水线；不同 d 之间因此相关，只用于标度曲线，配对推断在每个 d 内单独做。
- τ0 = 900 / 3400 / 6700 对应表 VI 的三档首级上下文（约 0.9k / 3.4k / 6.7k）；(·,·,8) 的格子让表 VI 的设计在第二个服务栈上完整重做一遍。
- 并发 16 只做 8 级，用于看显存压力下自动前缀缓存能否保住钉住状态。已知容量（由第 2 节算术推出）：32B-AWQ 单卡约 8 GB KV，并发 4、τ0 = 3400、32 级时总上下文约 36k token，接近或超过容量，**预期会出现抢占/驱逐**；这一格照跑照报，判读见 E5。

## 7. 端点与统计

- 重复单位是 rep。并发 c > 1 时先对同一 rep 内 c 个会话取均值。
- 配对对比：钉住（或存取）对重放，按 rep 配对，报节省 1 − T_trt / T_replay 的均值与 Student t 95% 区间（自由度 n−1），另报差值区间与 Wilcoxon 符号秩 p。
- T 取四种：整条流水线墙钟时间（主端点）、各级端到端之和、各级首 token 时间之和（预填充相，含排队）、各级解码时间之和。
- 深度标度：每个 rep 对 d = 2, 4, 8, 16, 32 的累计首 token 时间做 log-log 线性拟合取斜率，再对 rep 取均值与区间。
- 字节：分配器每 token 字节 = 可用 KV 显存（GiB，日志保留两位小数）× 2³⁰ × TP / KV 容量 token 数；与理论值之比。每会话状态字节 = 上下文 token 数 × 理论每 token 字节；应用上下文字节 = 上下文文本 UTF-8 字节。持有时间 = 钉住会话从第 1 级开始到第 d 级结束的墙钟时间。
- 汇总脚本 `summarize.py` 产出 `stage_records.csv`、`depth_pairs.csv`、`depth_contrasts.csv`、`exponents.csv`、`kv_bytes.json`。

## 8. 判读规则（结果出来之前定死）

**E1 每 token KV 字节（R2-3）。** 分配器值与理论值之比落在 0.98–1.02 内，就把理论公式当作该栈的实测确认；超出就报分配器值并写明差额。论文三档假设值与实测区间（5 个模型，bf16）比较：某档落在实测最小值与最大值之间记作「处在实测范围内」，高于最大值记作「高估状态成本（保守）」，低于最小值记作「低估」。三档对应哪个模型规模由仿真器的档位表决定，判读时从实验克隆的 `oran_mmas_sim.py` 核对后再写，不凭记忆对号。另报 FP8 下的每 token 字节，以及各深度下每会话状态字节对论文存储档位（250 MB 至 16 GB）能容纳多少会话。

**E2 只存上下文（F06/F08）。** 报应用上下文实测每 token UTF-8 字节，对照论文「每 token 4 字节」的假设；报 KV 字节与应用上下文字节之比。比值只陈述，不据此改论断。

**E3 深度标度（F04，式 (3)）。**
- token 工作量：钉住臂第 2 级起，每级 cached_tokens 占上一级上下文的比例在并发 1 的格子里 ≥ 0.95，记作「服务端确实只预填充新 token」，式 (3) 的 token 计量在该栈上成立；否则如实报比例。
- 时间：钉住臂累计首 token 时间的 log-log 斜率，95% 区间上界 ≤ 1.3 记作「在 d ≤ 32、所测上下文范围内与线性一致」；上界 > 1.3 记作「token 工作量线性，但实际时间超线性（注意力仍要读全部历史）」，此时式 (3) 只能写成 token 工作量近似。重放臂斜率照报，不设门槛（τ0 较大时在所测范围内本来就接近线性）。
- 节省随深度：每个 τ0 × 并发，节省(d=32) − 节省(d=2) 的配对区间不含 0 且为正，记作「节省随深度增长」；否则如实写「未分辨」。

**E4 表 VI 在第二个服务栈上的方向（F05）。** 8 级、各 τ0 与并发下，钉住对重放的整条流水线节省区间不含 0 且为正，记作「方向复现」。并发 4 对并发 1 的节省差为正且区间不含 0，记作「并发放大节省」复现。数值只在本表内比，不与 BRJD313 的 Ollama 数并列。

**E5 钉住能否被保证（F05/F06）。** 并发 16 及容量紧张的格子里，钉住臂后续级的命中比例 < 0.95 或出现抢占，记作「自动前缀缓存在显存压力下保不住会话状态，需要显式预留」；这是对状态坐标会绑定的直接观测，照实写，包括没有出现的情况。

**E6 主机存取（F06）。** 存取臂每级首 token 时间与钉住、重放配对比较。存取严格介于两者之间且对重放的节省区间不含 0，记作「主机驻留状态仍有加速器收益」；报每恢复一个 token 的额外首 token 时间（相对钉住）。不满足就照实报。

**E7 持有时间。** 只报数（各模型、各深度钉住会话的墙钟持有时间），供式 (1) 的占用项参考，不设门槛。

**通用。** 任何一条不满足预期都照报。缺格（服务起不来、量化核不支持等）在 DATA_PROVENANCE 里写原因，不补估计值。所有绝对数只标「4卡机、vLLM 0.30.0、本配置」。

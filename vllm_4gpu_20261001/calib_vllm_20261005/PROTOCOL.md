# R260401 统一服务栈测量协议（4卡机 vLLM，2026-10-05，开跑前写定）

## 缘由

用户 10-05 定：稿里在 DESKTOP-BRJD313 上用 Ollama 测的服务数字一律换成 4卡机 vLLM 一套服务栈。R260401 与 BRJD313 不再关联。被替换的是三处：

| 稿里位置 | 原数据（BRJD313，Ollama Q4_K_M） | 本协议的替代 |
|---|---|---|
| §V-A 服务标定与图 profile calibration | 120 次单流调用，Qwen3 0.6B–14B | calib：5 个模型 × 24 次 |
| §V-A 并发漂移（3.2 倍、10.1 倍；+148%、−22%） | 1.7B、4B，n=1/2/4/8 | drift：0.6B、4B、8B |
| §V-B 20 条真实 5 级流水线（96.5%） | qwen3:4b | pipelines：Qwen3-4B |

## 环境

4卡机（主机 `host`，4×RTX 5090 32 GB），vLLM 0.30.0（`~/venvs/vllm`），客户端用 `~/venvs/r260401_runner_20261003` 的 Python。每个任务一个模型、一张卡，由 NAS 发射 daemon 选卡。服务参数：`--max-model-len 8192 --gpu-memory-utilization 0.85 --seed 0`，自动前缀缓存保持默认开启；每次调用以唯一前缀开头，不会命中缓存。

## 模型

Qwen3-0.6B、Qwen3-4B、Qwen3-8B（bf16），Qwen3-14B-AWQ、Qwen3-32B-AWQ。4卡机上没有 Qwen3-1.7B 与 bf16 的 14B。标定按“模型 × 量化 × 服务栈”区分配置，与正文的标定键一致，所以精度不同的模型各算各的，正文按配置逐个写明。

## 测量

- **calib**：
  - 输入目标 40、160、640、1600 token，输出 16、64、256 token，每格 2 次，共 24 次单流同步调用；
  - 温度 0，`ignore_eos`，流式接收；
  - 首 token 时间记为预填充时间，最后与第一个 token 的时间差记为解码时间；
  - 预填充时间对实际输入 token 数、解码时间对输出 token 数分别做一次线性拟合，报告斜率、截距与 R²。
- **drift**（0.6B、4B、8B）：
  - n = 1、2、4、8 路同时发出同一负载（约 512 输入 token，唯一前缀；128 输出 token，温度 0，`ignore_eos`），每档 3 次；
  - 报告每次调用墙钟时间与 n=1 之比，以及总输出吞吐相对 n=1 的变化。
  - 与 BRJD313 原稿一样，只报同一服务器上的比值。
- **pipelines**（Qwen3-4B）：
  - 4 个主题 × 5 条路径，每条 5 级（计划、初稿、批评、修订、总结）；
  - 每级一次 chat 调用，内容为唯一前缀 + 全部累积上下文 + 本级指令；
  - 思考关闭，温度 0.7，种子为 路径号×100+级号，最多 256 输出 token；
  - 记录每级输入与输出 token 数。重放与 AFS-C 的上行字节按 `analysis/afsc_trace_replay_20260803.py` 的同一口径计算。

## 判读

三项都是描述性测量，不设通过门槛。数字只属于 4卡机这一配置，正文写明“vLLM 0.30.0，RTX 5090，单卡”，不与任何 Ollama 数字并表。原稿里的定性说法（预填充与解码斜率随模型规模增长；不存在通用的并发修正；实测流水线的节省高于合成基线）按新数据重新核对：成立就保留，不成立就照新数改写。
